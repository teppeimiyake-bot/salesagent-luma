# 入金管理 Phase 10：スプレッドシート準拠に作り直し（社長承認 2026-06-04）

## 背景・問題
Phase 9 で「受注DealProduct全件(129)」から入金エントリを自動生成した結果、スプレッドシート（入金管理＝57行 / 定期＝11行）に無い過去案件まで空エントリが大量発生し、シートと不整合（dpidエントリ129のうち入金状況入力済は30だけ）。

## 正しい考え方
**スプレッドシートが入金管理の正本**。1行＝1入金案件。**同一顧客で複数案件があるとき、シート側が既に複数行に分けている**（例：JMAC・東急リニューアルが2行）。つまり「プロダクト/案件ごと」の粒度は**シートの行がそのまま満たす**。CRMの受注プロダクト全件から生成するのは誤り。

## 実装方針
1. **入金管理の表示＝シート由来の行**（`source_key` が `spot::` / `recurring::` の57＋11行）を正とする。Phase9で入れた「受注プロダクト全件の dpid:: エントリ」は**廃止**。
   - 一覧API(GET)の絞り込みを `dealProductId IS NOT NULL`（dpid行）から **シート由来行（source_key like 'spot::%' / 'recurring::%'）** に変更。
   - 自動生成された dpid:: の余剰エントリ（スポット約72・定期約8の空行）は**クリーンアップ（削除）**。dev/本番とも。
2. **各シート行を 商談・プロダクト・企業に紐付け**：
   - `customerName`（シートの顧客名＝会社名。dpidと違い商材名ではない）から企業を解決 → `companyId`、その受注商談 → `dealId`、可能なら受注プロダクト（カテゴリ推定 or 単一受注なら確定）→ `dealProductId` を設定。
   - 顧客名表示＝`company.name ?? customerName`（未紐付けでも顧客名は出る）、プロダクト名列＝`dealProduct.productName`（紐付いた場合）。
3. **未紐付け企業の解消（重要）**：スポット21社・定期4社が表記ゆれで未マッチ。`normalizeName`（company-dedup）＋手動マッピング表（`scripts/payment-company-aliases.ts` 等）で企業マスタに当てる。確実に1社へ絞れる場合のみ紐付け、なお不能なものは顧客名そのまま表示＋未紐付けレポート出力（社長へ社名対応を確認）。
4. **最新シートで再同期**：`docs/payment-mgmt/入金管理_spot.csv` / `入金管理_recurring.csv`（最新取得済・前回と差分なし）から、送付状況/着金状況/支払時期/各日付/金額を **upsert で上書き同期**（`source_key` キー）。今後の再取り込みも同手順で最新化できるようにする。
5. **金額連動・PM連動・期日アラート・admin限定・色分け・フィルタ（Phase 8/9の機能）は維持**。契約金額の「提案金額連動/再同期」「納品予定日PM連動」「定期の期間/金額検算」はシート行にも効くようにする（dealProduct/ProductionProject 紐付け後に機能）。

## 完了条件
- 入金管理の表示件数が **スプレッドシートと一致（スポット57 / 定期11、シートが複数行の顧客はその通り複数行）**。空の余剰エントリは出ない。
- 各行の送付/着金/金額/日付が**シートと一致**。顧客名＝会社名、プロダクト名は紐付いた分だけ表示。
- 未紐付けの残り社数を報告（社長へ社名対応を仰ぐ）。
- `tsc`/`build` PASS。dev検証。本番反映（再シード＋余剰削除）はオーケストレーター（私）が SEED_ALLOW_PROD=1 で実施。push しない。

## 注意
- 既存実データ破壊禁止（企業/商談/ユーザ）。余剰 dpid:: 入金エントリの削除のみ（source_key で厳密に対象限定）。冪等。
- 本番では余剰 dpid:: 129-57相当の削除＋シート行の紐付け更新が走る。dev で件数確認後に本番。
